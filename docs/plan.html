Core Strategies

Recommended

1. GitOps with Kustomize Overlays

Use ArgoCD or Flux with a per-tenant overlay structure. Each tenant pins specific image versions without duplicating base manifests.

deploy/
  base/
    payment-service/
    auth-service/
  overlays/
    # per-tenant version pins
    tenant-acme/
      kustomization.yaml
    tenant-globex/
      kustomization.yaml
  • No manifest duplication
  • Git history = audit trail
  • PR-based version promotions
Simple Start

2. Helm + Per-Tenant Value Files

Each tenant gets a dedicated values file that pins image tags. A CI pipeline runs helm upgrade per tenant.

charts/payment-service/
values/
  tenant-acme.yaml
  # image.tag: v1.2.3
  tenant-globex.yaml
  # image.tag: v1.4.0
  • Easy to understand
  • Harder to audit at scale
  • Good for smaller tenant counts
Scalable

3. ArgoCD ApplicationSets

Define tenants in a config directory. ApplicationSets auto-generate one ArgoCD Application per tenant. New tenant = new folder.

generators:
  - git:
      files:
        - path: "tenants/*/config.json"

# config.json specifies:
# cluster, namespace, versions
  • Zero manual ArgoCD setup per tenant
  • Scales to hundreds of tenants
  • Single source of truth

Multi-Cluster Management

Since your microservices span multiple EKS clusters, additional patterns apply:

ArgoCD Hub-Spoke Mode

Run one central ArgoCD instance that manages all downstream clusters. Avoids the overhead of running ArgoCD on every cluster.

argocd-hub (central)
  ├── cluster-us-east-1   (tenant A, B)
  ├── cluster-eu-west-1   (tenant C)
  └── cluster-ap-south-1  (tenant D, E)

Cluster Routing via ApplicationSet

Use cluster selectors in your ApplicationSet generator to route each tenant's workload to the correct cluster based on a label or config value.

Infrastructure as Code

If clusters are provisioned per tenant, manage cluster lifecycle alongside app deployment using Terraform or Crossplane.

💡 Tip: Tag your EKS clusters consistently (e.g., tenant=acme, region=us-east-1) so ApplicationSet selectors remain readable and maintainable.

Version Tracking — Source of Truth

You need a single place that answers: "which tenant runs which version of which service?"

  • Git tenants/ directory — auditable, PR-driven, works natively with ApplicationSets
  • Lightweight config service / database — useful if versions change programmatically
  • Spreadsheet — fine to start, painful at scale, migrate away early

Practical Recommendation

✅ Recommended Stack (EKS + GitOps)

Given you're already on EKS, this combination gives you audit trail, PR-based promotions, and a single pane of glass across all clusters and tenants:

  1. ArgoCD in hub-spoke mode — one control plane across all EKS clusters
  2. ArgoCD ApplicationSets — auto-generate one app per tenant from a tenants/ directory
  3. Kustomize overlays — per-tenant image version pinning without manifest duplication
  4. Git as the version registry — all version changes go through PRs, giving you history and rollback for free

Benefits of This Approach

  • Version history is in git — no "who changed what" mysteries
  • Promote a tenant to a new version via a PR — reviewable and reversible
  • Onboard a new tenant by adding a folder — no manual cluster or ArgoCD config
  • Single ArgoCD UI shows all tenants across all clusters
  • Works with any CI/CD system that can open a PR or push to git
Part 2

Testing on Your Laptop

kind (Kubernetes IN Docker) is the best fit for local testing — it lets you spin up multiple clusters with minimal overhead, directly mirroring your multi-cluster EKS setup.

Prerequisites

# Install everything you need (macOS)
brew install kind kubectl helm argocd
brew install --cask docker   # if not already installed

Step 1 — Spin Up Two Clusters

Create clusters

# Simulates hub + one tenant cluster
kind create cluster --name hub
kind create cluster --name tenant-cluster-1

# Verify both are up
kubectl config get-contexts

Step 2 — Install ArgoCD on the Hub

Deploy ArgoCD

kubectl config use-context kind-hub

kubectl create namespace argocd
kubectl apply -n argocd -f \
  https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Wait for it to be ready
kubectl wait --for=condition=available \
  --timeout=120s deployment/argocd-server -n argocd

# Expose the UI locally
kubectl port-forward svc/argocd-server \
  -n argocd 8080:443

Get login credentials

# Open https://localhost:8080
# Username: admin
# Get initial password:
argocd admin initial-password -n argocd

# Login via CLI
argocd login localhost:8080 --insecure

Step 3 — Register the Spoke Cluster

Add tenant-cluster-1 to hub

# Registers the second cluster
# so ArgoCD can deploy to it
argocd cluster add kind-tenant-cluster-1

Step 4 — Set Up a Minimal GitOps Repo

Push a test repo to GitHub (or use a local git server). Use this structure:

my-gitops-repo/
  base/
    deployment.yaml       # simple nginx deployment
    kustomization.yaml
  overlays/
    tenant-a/
      kustomization.yaml  # sets image tag: v1.0
    tenant-b/
      kustomization.yaml  # sets image tag: v1.1
  tenants/
    tenant-a/config.json  # { "tenant": "tenant-a", "clusterURL": "..." }
    tenant-b/config.json

Step 5 — Apply an ApplicationSet

applicationset.yaml

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: tenants
  namespace: argocd
spec:
  generators:
    - git:
        repoURL: https://github.com/you/my-gitops-repo
        revision: main
        files:
          - path: "tenants/*/config.json"
  template:
    metadata:
      name: "{{tenant}}"
    spec:
      project: default
      source:
        repoURL: https://github.com/you/my-gitops-repo
        targetRevision: main
        path: "overlays/{{tenant}}"
      destination:
        server: "{{clusterURL}}"
        namespace: "{{tenant}}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true

🚀 Quickest Path to Something Working

  1. Install Docker + kind + kubectl + helm on your Mac
  2. Run kind create cluster --name hub — you don't even need a second cluster to start
  3. Install ArgoCD and port-forward to localhost:8080
  4. Point it at a GitHub repo with a base deployment + one overlay
  5. Apply the ApplicationSet and watch ArgoCD sync it automatically
💡 Once this works locally, adding a second kind cluster and hub-spoke wiring is straightforward. All concepts transfer 1:1 to EKS — you're just swapping kind create cluster for actual EKS clusters.
